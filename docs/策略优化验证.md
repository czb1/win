## 修正内容

| 问题 | 新行为 | 验证依据 |
| --- | --- | --- |
| 三座武器已建齐，金币低于 25 仍触发一矿一卖 | 按批次出售；确有空闲建造点且售出所得足以补造武器时可提前出售 | 新增经济回归用例、70 回合受控回放 |
| 工人刚挖到一块石头就长途返回造墙 | 仍在可采石矿旁时补齐批次，再返回；矿消失或停产则使用已有石料 | 单石继续采集、批次齐备离矿用例 |
| 墙位全在建造失败退避中，仍为造墙挖石头 | 只为当前可尝试的空位准备石料，转入普通经济活动 | 失败墙位回归用例 |
| 缺少操控者时，距离相同可因低武器 ID 选中冷却武器 | 优先分配本回合可以实际开火的火力，再比较移动距离 | 一名角色、冷却火箭、就绪电磁炮用例 |
| 火箭仅以机器人所在格为落点候选 | 枚举机器人周围九格内的合法落点，考虑空地聚怪中心与射程边缘溅射 | 四角机器人空中心、目标在落点射程外一格用例 |
| 电磁炮把其他武器的计划伤害当作已扣血，虚增穿透 | 按请求中的当前血量消耗能量，仅将未覆盖的有效伤害计入选点价值 | 前排血量 40、已有计划伤害 30、能量 40：后排预测伤害应为 0 |
| 伤害计划在攻击指令校验前写入共享估计 | 只有账本成功接纳攻击才影响后续武器的集火估计 | 代码审查；共享角色锁和指令合法性由原测试覆盖 |

矿点完全不可用时允许出售已有的零散矿石，避免等不满一个批次而闲置。矿石不足以补造武器时继续积累，避免低价值往返。商品价格、武器射程、攻击力仍采用当前请求数据。

电磁炮规则依据为仓库任务书 §4.4 的回合末统一伤害结算，以及 §4.5.4 的能量消耗规则；火箭规则依据为 §4.5.4 的中心 20、周围八格 10、重叠可叠加。弹道边界仍沿用原有保守模型，需由引擎实测确认。

## 实测结果

环境：Python 3.12.14，仅标准库；本轮未在比赛指定的 Python 3.11.10 上执行。

- 原版已有 40 项测试通过。
- 修改前新增的 7 项问题复现场景全部失败；修改后全部通过。
- 补充 5 项经济边界用例后，完整测试共 **52 项通过**，耗时 0.966 秒。
- 原有 1300 回合静态状态协议检查通过，单次最慢 0.71 毫秒。这不是连续生存模拟。
- `tools/replay.py examples/request.json` 正常生成包含三字段的响应。
- `git diff --check` 通过。

### 受控经济回放

使用同一初始状态运行实际 `Agent.decide` 70 个白天回合：一名工人、三座既有武器、一个小贩、铜价 5、初始金币 0、无建造点。铜矿每采集十次在两个附近坐标之间轮换。脚本只应用移动、采集、出售；无对手、机器人、新闻、商店升级和任务。这是用于隔离经济往返损耗的人工场景。

| 指标 | 原版 | 修正后 |

| 实际卖出所得金币 | 20 | 120 |
| 采集次数 | 4 | 30 |
| 移动次数 | 58 | 33 |

这些数值只说明该场景中的往返效率改善，不能外推成实战收入倍率或胜率。

### 密集机器人耗时

41×32 地图、740 个静止机器人、三种三级武器、20 个不同回合号以避开重复请求缓存。未模拟伤害、移动或冷却变化。

| 指标 | 原版 | 修正后 |
| --- | ---: | ---: |
| 20 次决策中的最慢耗时 | 252.73 ms | 112.05 ms |
| 每次输出攻击的武器数下限 | 3 | 3 |

缓存每个候选落点的物理命中集合，避免每枚弹药重复计算全部弹道／溅射；该样本中即使增加操控者火力评估，总耗时仍下降。单次本地耗时测量不是硬实时保证。

## 仍需实战确认

目前最大的接入不确定性仍是内网图片中的合法建造区域与建筑参数。默认推导布局可能被判为执行失败；策略优化不能替代坐标核对。应提供建筑区域图，或按 `config/explicit-layout.example.json` 填写经过引擎确认的坐标与造价。

下一轮针对败局优化需要连续请求／响应，尤其是第一夜前后的金币、建筑状态、`lastRoundRoleActionResults`、`errors`、基地血量和最终得分。这样才能区分建造失败、返防不及时、火力不足和任务得分落后。
